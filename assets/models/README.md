# Model assets

Drop hand-authored (or generated) animated models here to replace the
built-in procedural sprites, no call-site changes required. Loading is
resolved by `UnitRenderRepository` (`lib/core/rendering/domain/repos/`),
implemented by `CompositeUnitRenderRepositoryImpl`
(`lib/core/rendering/impl/`), which tries a `.riv` (Rive) model, then a
`.json` (Lottie) model, then falls back to the caller-supplied procedural
sprite:

- `ally_<kind>.riv`/`.json` and `enemy_<kind>.riv`/`.json` - e.g.
  `enemy_soldier.riv`, `ally_tank.json` (`<kind>` names come from
  `UnitKind` in `lib/core/combat/unit_kind.dart`; enemy vs. ally is
  distinguished by team, not by enum, so both prefixes share the same
  `UnitKind` names).
- `tower_<type>.riv`/`.json` - e.g. `tower_machineGun.riv`,
  `tower_trainingCenter.json` (`<type>` names come from `TowerType`/
  `BuildingType` in `lib/features/towers/domain/models/`, both of which
  implement the shared `UnitType` marker). This only replaces the tower's
  base plate; the turret stays procedural since its rotation logic depends
  on it being a separate component.

`.riv` (Rive) files are tried first, then `.json` (Lottie). If neither
exists for a given key, the existing procedural sprite is used - nothing
changes visually until a file exists here.

## Lottie assets (generated)

Every `ally_*.json`/`enemy_*.json`/`tower_*.json` file currently in this
folder was generated by `tool/lottie_gen/` (`gen_units.py` for mobile
units, `gen_towers.py` for tower/building base plates) - a Python script
that faithfully ports the existing procedural `Canvas`-paint shape recipes
into static (single-frame) Lottie/Bodymovin JSON. Regenerate with:

```
tool/lottie_gen/.venv/bin/python3 tool/lottie_gen/gen_units.py
tool/lottie_gen/.venv/bin/python3 tool/lottie_gen/gen_towers.py
```

These files are static - all per-frame motion (bobbing, rotor spin,
recoil) stays owned by Flame, not the Lottie timeline. Since a live
`LottieComponent` would repaint the whole vector shape tree every frame
for every on-screen instance, `LottieUnitRenderRepositoryImpl` instead
rasterizes each composition to a cached `ui.Image` once per key and reuses
it after that - runtime cost per instance is identical to a plain
`SpriteComponent`. `test/lottie_model_assets_test.dart` loads every file
here through the real `lottie` package as a regression check.

No `.riv` (Rive) files ship with the game today - `.riv` is a compiled
binary format normally hand-authored in the Rive editor app, not something
this generator pipeline can produce.
